前回、Reference Implementationは完成品ではなく、**Foundryの成立条件を探すためのEvidence Sourceでもある**という話を書いた。 RI#1はArticle Production。RI#2はDocumentation Production。RI#3はVisual Asset Production。RI#4はResearch-Grounded Long-form Content Production。 ここまで仕事を変えれば、当然、問題も全部変わると思うじゃん？ ワシもそう思っていた（笑）。 記事を書くAIと、Internal文書からPublic文書を作るAIと、画像を生成する仕組みと、検索結果を根拠に長文を書く仕組み。使うToolも違う。Outputも違う。Qualityの見方も違う。だったら、それぞれ別の問題を解けばいいはずだった。 ところが実際に横へ広げていくと、妙なことが起きた。 **また、そこか。** 仕事内容は変わっているのに、AIへ仕事を任せた時に詰まる場所が、何度も似た位置に出てくる。 何を任せたのかが曖昧になる。 Humanが決めた値が、実行地点まで届かない。 Machineで判定できることを、LLMへもう一度考えさせる。 Technical Gateを通ったのに、人間は「違う」と言う。 Reviewしたはずなのに、そのReviewが何を見たものなのか、後から一意に追えない。 一個ずつ見れば、ぜんぜん別のバグだ。 でも四つの仕事を横に並べると、だんだんそう見えなくなってきた。

## 1. 仕事を変えれば、壊れ方も変わると思っていた

RI#1を作っていた頃は、起きる問題の大半をArticle Production固有の問題として見ていた。 文字数が合わない。Researchの出力が足りない。Retryしたら逆に長くなる。Workflowの途中で必要なfieldが消える。PublishedしたのにRuntimeで思ったものが動かない。 そりゃ記事生成Workflowを作ってるんだから、記事生成の問題が出るよな、と。 そこでContractを作り、DTOを作り、Normalizeを入れ、Gateを置き、Retryを直し、Evidenceを取るようになった。 Season 1では「AIを賢くすれば解決する」から離れて、**壊れない構造を作る**方向へ進んだ。 Season 2ではさらに、Repository、Draft、Published、Runtime、Current Snapshot、Human Decisionまで扱うようになった。 それでもワシの中にはまだ、
> これは記事生成が複雑だから、こんなに面倒なんじゃないの？
という疑いが残っていた。 そこで仕事を変えた。 文書へ行った。 画像へ行った。 Researchへ行った。 結果。 **もっと分かりやすく同じ問題が出てきた（笑）。**

## 2. RI#1――決めたはずのことが、実行地点でズレた

RI#1で強烈だったのは、**「Contractがある」ことと「そのContractで実行される」ことは別だった**という話だ。 Formal TestではHumanがExact Inputを決めていた。 ところがLauncher側には、別のgenericなInputを選べる余地が残っていた。 Humanは決めている。 Contractにも書いてある。 でもExecution Pointでは、まだ選び直せる。 これ、地味に見えてかなり怖い。

```text
Human Decision
↓
Contract
↓
……ここまでは正しい
↓
Execution Point
↓
別の値を選べる

```

「決めた」が「実行された」に変わる途中で、意味が抜ける。 Published Identityでも似たことが起きた。 新しいPublished Stateが成立しても、Launcherが古いIdentityを参照していれば、実際に叩く先は古いままだ。 RepositoryがPASSした。 Draftも合った。 Publishedも合った。 それでもExecution Bindingが古ければ、Runtimeは別のものを動かせる。 さらにRetryでは、Machine側では初回出力が何文字で、上限が何文字で、最低どれだけ削る必要があるか分かっていた。 なのに、それをLLMへ再推定させた。 するとモデルは前提を誤認し、短くするRetryなのに、出力がさらに長くなった。 このへんまで来ると、問題は「文章が下手」とか「LLMがポンコツ」じゃない。 **Machineが確定できるControl Factと、AIへ任せるSemantic Workの境界を分けていなかった。** 当時はRI#1のRuntime問題として直していた。 でも、後から見るとこれが最初の大きなヒントだった。

## 3. RI#2――文章が書けても、仕事としては成立しない

次にRI#2、Documentation Productionへ移った。 ここではAIの文章力だけを見ても意味がない。 InternalのCanonical Sourceを読んで、Publicへ出せるものを選び、必要ならMaskやGeneralizeを行い、変更Scopeを守り、Reviewを通して、Humanへ渡す。 文章として綺麗でも、Sourceにないことを書いたらアウト。 正しい内容でも、変更してはいけない場所まで変えたらアウト。 昨日のSnapshotを「Currentです」と扱ったらアウト。 記事生成なら「いい感じに補完した」が武器になる場面もある。 Documentationでは、それが事故になる。 ここでまた同じ問いが出た。 **AIへ何を任せ、何を任せてはいけないのか。** Sourceから意味を読み取る。 Public向けに分かりやすくする。 文章を組み立てる。 そこはAIが強い。 でも、

```text
どのSourceがCurrentか
どの範囲を変更してよいか
何を公開してよいか
どのEvidenceを満たせば次へ進めるか

```

まで「いい感じに判断して」で渡すと危ない。 つまり記事とは全然違う仕事なのに、また、
> **委譲する仕事のContractを実行前に固定しないと壊れる**
という場所へ戻ってきた。 そしてRI#2ではもう一つ、Runtime Capabilityそのものも問題になった。 「このModelならこのくらい出来るはず」という静的な想定ではなく、Current Runtimeを実際に観測・測定し、そのEvidenceからEffective Capabilityを決めて、後続へBindingする。 この考え方が後に**FC-CORE-001 Runtime Capability Calibration**として残る。 でも、その時はまだ「Foundry Coreを発見した！」なんてノリじゃない。 目の前の仕事を成立させるために必要だったから、やった。 それだけだった。

## 4. RI#3――Gateを通った。でも「これじゃない」

RI#3で画像へ行った時、今まで文章やDocumentationの中に埋もれていた境界が、いきなり目で見えるようになった。 顔が画面内に入っている。 胴体が不自然に切れていない。 要求したFraming条件を満たしている。 Technical GateはPASS。 で、画像を開く。 **いや、これじゃねぇだろｗｗｗ** となる。 ここは本当に分かりやすかった。 Machineが判定できる条件としては成立している。 でも、人間が最終成果物として採用するかは別だ。 構図が気に入らない。 表情が違う。 自然さが足りない。 目的に合っていない。 Technical Gateをどれだけ厳密にしても、そのすべてを数値条件へ押し込めることはできない。 逆に、人間が最後に見るからといって、顔がフレーム外に出ていないか、必要条件を満たしているかまで毎回目視で全部確認する必要もない。 ここで、

```text
Technical Gate
≠
Human Acceptance

```

が、ものすごくはっきりした。 しかもFoundryConsoleを作る過程でも、Humanが裏側のComfyUIやRuntime Parameterを全部直接触る必要はないことが見えてきた。 人間に必要なのは、Purposeを指定し、選択肢を選び、進捗を見て、Gate結果を確認し、最後に採用を判断できること。 裏側の処理をHumanが全部操作することではない。 これも別の言い方をすれば、
> **HumanがAuthorityを持つことと、Humanが全Stepを操作することは別**
という話だった。 記事生成から一番遠そうな画像制作まで来て、また同じ「境界」の話をしている。 この辺から、さすがに偶然には見えなくなってきた。

## 5. RI#4――検索できても、根拠がつながっていなければ危ない

RI#4は今も**ACTIVE VALIDATION / CURRENT FRONTIER**にいる。 だから、ここだけは完成した話として書かない。 今扱っているのはResearch-Grounded Long-form Content Production。 検索する。 Sourceを取る。 Entityを確認する。 Freshnessを見る。 根拠を文章へBindingする。 Reviewする。 長文としてまとめる。 検索結果が返ってきた時点では、何も終わっていない。 同じ名前の別Entityかもしれない。 古い情報かもしれない。 Source自体は正しくても、そのSourceが支えていない主張まで文章が広がっているかもしれない。 Reviewも同じだ。 「Review PASS」という文字だけ残っていても、

```text
何をReviewした？
どのArtifact？
どのRevision？
どのSub-artifact？
その結果は、どのDecisionへ使われた？

```

が追えなければ、後から見た時に意味が弱い。 今、**Review Binding Integrity**が`CANDIDATE — STRONG`のままConfirmed Coreへ上がっていない理由もここにある。 かなり強い。 複数の仕事で必要性が見える。 でも、RI#4にはまだReview BindingのEvidence locator gapが残っている。 だから先にCore扱いしない。 この「まだ上げない」という判断自体も、Season 3では大事だと思っている。 ワシらは今、Coreを増やす競争をしているわけじゃない。 **仕事を変えても本当に残るものだけを、Evidence付きで上へ持っていこうとしている。**

## 6. 違う仕事なのに、同じControlが何度も出てきた

四つを並べる。

```text
RI#1 Article Production
RI#2 Documentation Production
RI#3 Visual Asset Production
RI#4 Research-Grounded Long-form Content Production

```

Outputは全部違う。 でも、壊れた場所を一段抽象化すると、かなり似ている。

### 実行前

何を任せるのか。 何を成果とするのか。 どこまでAIが判断してよいのか。 失敗したらどこで止まるのか。 これが曖昧だと壊れる。 → **Delegation Contract Binding**

### 実行中

Machineで正確に判定できることを、LLMへ再推定させない。 条件を満たしていないArtifactを「まあ成功」で後ろへ流さない。 → **Deterministic Technical Gate**

### 実行後

何を実行し、何が出て、どのGateを通り、何をReviewし、Humanが何を決めたのか。 後から再構成できなければ、次の判断に使えない。 → **Evidence Traceability** そしてそのさらに手前に、 「そもそもCurrent Runtimeで何が出来るのかを、推測ではなく測れ」 がある。 → **Runtime Capability Calibration** 現在Confirmedになっている、

```text
FC-CORE-001 Runtime Capability Calibration
FC-CORE-002 Delegation Contract Binding
FC-CORE-003 Deterministic Technical Gate
FC-CORE-004 Evidence Traceability

```

は、こうして見ると「偉い人が最初に設計したFoundry原則」ではない。 **別の仕事をやるたびに同じような所で詰まり、そこを直したものを横に並べた結果、最後まで残ったControlだ。** ここが、ワシはかなり面白い。

## 7. 「AIが苦手」ではなく、「境界が曖昧」だった

初期のワシなら、こういう失敗を見ると、 「AIって意外と指示守らないな」 「モデル変えれば良くなるかな」 「もっと強いPromptにすればいいか」 と考えていたと思う。 もちろん、Model CapabilityやPrompt品質は重要だ。 でも、四つの仕事を横断して見えてきた問題は、それだけではなかった。 Humanが決める場所。 AIが意味を作る場所。 Machineが正確に判定する場所。 Runtimeが実際に動く場所。 Reviewが意味を確認する場所。 Evidenceとして残す場所。 この境界が曖昧なまま、 **「AI、あとはよろしく」** とやると壊れる。 しかもAIは、かなりそれっぽく埋めてくれる。 ここが厄介だ。 値が無ければ推測する。 Targetが曖昧なら選ぶ。 情報が足りなければ補完する。 文章として自然になる方向へ広げる。 Semantic Workでは、それがAIの強さだ。 でも、すでに決まったID、Threshold、Scope、Current Source、Acceptance条件まで同じ調子で補完されたら困る。 だからFoundryで必要なのは、AIを全部縛ることじゃない。 **自由にしていい場所と、自由にしてはいけない場所を分けること**なんだと思う。 意味はAIに任せられる。 Controlまで曖昧にしない。 Humanは全部を操作しなくていい。 でもAuthorityまで手放さない。 Machineに出来ることはMachineへ渡す。 でもHuman AcceptanceまでMachineへ押し込まない。 四つのRIをやって、ようやくこの輪郭が見えてきた。

## 8. ここからFoundry Coreの話が始まる

Season 3の第1話では、記事を作らなくなったあとに何を作るのかを書いた。 第2話では、Reference Implementationは完成品ではなくEvidence Sourceでもある、と書いた。 そして今回、ようやくそのEvidenceを横に並べ始めた。 結果、仕事が変わっても同じ場所で壊れた。 いや、正確には、 **壊れ方は違う。でも、壊れているControl Boundaryが似ていた。** これがCross-RI Evidenceの面白いところだと思う。 一つのWorkflowだけ見ていたら、「このWorkflow固有のバグ」で終わっていたものがある。 別の仕事へ持っていったことで、
> あれ？
>
> これ前にもやったぞ？
となる。 さらに別の仕事でも出る。 そこで初めて、
> これ、記事用でもDocumentation用でも画像用でもないんじゃね？
という疑いが出る。 その疑いをEvidenceで潰して、RI固有Implementationを剥がし、仕事を越えて残ったRuleだけを持ち上げる。 それが今やっているFoundry Core Extractionだ。 そして次は、その入口にある話へ行く。 AIへ仕事を任せる前に、まず確認しなければならないものがある。 Promptでもない。 Workflowでもない。 **そのRuntime、本当にその仕事が出来るの？** 次回。 **S3-04「AIに任せる前に、実行環境を測れ」** ここから、最初のConfirmed Core――**Runtime Capability Calibration**を掘る。
