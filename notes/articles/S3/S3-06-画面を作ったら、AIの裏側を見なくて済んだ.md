前回は、Technical Gateを通ったからといってHumanが成果物をAcceptするとは限らない、という話を書いた。Machineが一意に判定できることはMachineへ渡し、採用する、公開する、Riskを取るといったAuthorityはHumanへ残す。さらにHuman Gateを置きすぎると、AIへ仕事を任せる仕組みなのに人間が毎Stageで操作するHuman-operatedな仕組みへ戻ってしまうことも分かった。

そこで「Humanが見る場所を減らす」という方向へ進んだ。ところが、実際にRI#3 Visual Asset ProductionのFoundryConsoleを作っていくと、次の問題がすぐ出てきた。**Humanが見るべき場所だけ残したとして、そのHumanは何を見て、どこを触ればいいんだ？** Authority Boundaryを決めただけでは、まだ人間が使う画面にはなっていなかった。

今回は、その境界を実際の画面へ落としていく中で、Human-facing Control Surfaceという考え方へ辿り着いた話である。

## 1. Humanが見る場所を減らした。で、どこで見るの？

S3-05で分けたかったのは、HumanとMachineの仕事だった。ファイル名が一致しているか、Countが合っているか、決められた条件を満たしているか。こういう一意に決まる確認はMachineへ寄せる。一方で、「この画像を使うか」「この成果物を公開するか」「この変更を受け入れるか」はHumanが決める。考え方としてはかなり整理された。

でも、実際の運用ではHumanが判断するための入口が要る。画像をAcceptするなら、何を見てAcceptするのか。STOPしたなら、なぜ止まったのか。進行中なら、今どのStageにいるのか。HumanがAuthorityを持っていても、その判断材料がBackendのログや別々のToolへ散っていたら、結局人間が裏側を巡回することになる。

ここで一つ妙な状態になった。Human Gateは減らしたのに、Humanの仕事はあまり減っていない。確認ポイントの数を減らしても、必要な情報を探すためにComfyUIやログや出力Folderを行ったり来たりしていたら、操作負荷は残る。**Authority Boundaryを整理した次には、そのAuthorityを使うためのSurfaceが必要だった。**

## 2. 見えるようにしたら、今度は見えすぎた

FoundryConsoleでは、かなり早い段階から「処理フローを見えるようにしたい」という要求があった。Stageがどこまで進んでいるか、何を実行しているか、Artifactが出来たか、Gateはどうなったか。AIが裏で何をしているか全く分からない状態では、止まった時にも判断出来ない。だから最初は、見える情報を増やす方向へ進んだ。

ところが、この考えをそのまま伸ばすと画面がすぐにうるさくなる（笑）。Model、Prompt、Parameter、Node、Queue、内部ID、Temporary File、細かいRetry状態、Raw Log。Backendには必要な情報でも、それを全部Human-facingな画面へ出した瞬間、人間は「仕事を進める人」ではなく「AI Runtimeの監視員」へ戻ってしまう。

ここで「透明性」という言葉も少し考え直した。全部を常時表示することが透明なのではない。必要になった時にEvidenceや詳細へ辿れることと、普段の判断画面へ全部を並べることは別である。**見えなくしてはいけない。でも、いつも見せる必要もない。** この区別を入れたことで、画面設計の方向が変わった。

## 3. 欲しかったのはBackendの操作盤ではなかった

ワシがやりたいのは、ComfyUIのNodeを毎回操作することではない。Model Parameterを一個ずつ眺めたいわけでもない。画像を作る仕事なら、今どこまで進んでいて、何が出来上がり、何を自分が判断しなければならないのかが分かればいい。つまり欲しかったのは、Backendを操作するための画面ではなく、**仕事をControlするための画面**だった。

この違いは小さく見えて、かなり大きかった。Backendの複雑さをHuman-facing Surfaceへそのまま写すなら、内部機能が増えるたびに画面も複雑になる。でも「HumanがPurpose、Judgment、Responsibilityを保持するために何が必要か」から逆算すれば、Backendが複雑になってもHuman側まで同じ密度で複雑になる必要はない。

ここからHuman-facing Control Surfaceを、単なるUI改善ではなく**Authority Boundaryの表示面**として見るようになった。何をHumanへ見せるか。何をHumanに選ばせるか。どの処理は承認済み条件の中でMachineが進めるか。どこを越えたらHumanへ戻すか。前回まで文章で整理していた境界が、そのまま画面の構成要素へ変わっていった。

## 4. SHOW / HIDE――判断に必要なものだけを表へ出す

最初に分けたのがSHOWとHIDEだった。基準は「表示できるか」ではなく、**Humanが判断するために普段から必要か**である。Current Stage、Progress、Gate Result、STOP Reason、Artifact Statusのように、今の仕事の状態を判断するために必要な情報はSHOWへ置く。一方、Raw Prompt、Model Parameter、Node Graph、内部ログ全文のようなBackend情報は通常画面からHIDEへ回す。

HIDEは削除ではない。問題が起きた時に詳細へ降りたり、Evidenceを確認したり出来る道は残す。普段の画面では情報量を抑え、必要になった時だけ裏取りへ進める。これならHumanは毎回Backendの全貌を読む必要はないが、ブラックボックスにもならない。

この整理をすると、「情報を増やせば安心」という発想から離れられた。判断に不要な情報が増えると、本当に見るべきSTOPやArtifact Previewが埋もれることもある。Human-facingな画面では、情報量そのものより**判断材料の優先順位**の方が重要だった。

## 5. CONTROL / AUTO――Humanが押す必要のないボタンを消す

次に分けたのがCONTROLとAUTOだった。画面を作ると、出来る操作を全部ボタンにしたくなる。Start、Validate、Save、Convert、Retry、Export、Accept、Reject、Return。機能として存在するものを全部並べると、「操作出来る」という意味では立派だが、人間は何を毎回選ぶ必要があるのか分からなくなる。

そこで、S3-05で整理したAuthority Boundaryをそのまま使った。**Humanが毎回選ぶ意味がある操作だけをCONTROLへ残す。承認済み条件の中で機械的に一意に進められる処理はAUTOへ回す。** AUTOは「人間が責任を放棄する」という意味ではない。Humanが先に決めたScopeや条件の中で、MachineがMechanical Continuationするという意味である。

この区別を入れると、Human-directedとHuman-operatedの差が画面でも見えるようになった。Human-directedでは、HumanがPurposeと重要なDecisionを握る。しかし、そのためにValidateボタンやSaveボタンまで毎回押す必要はない。**Authorityを持つことと、全工程のクリック係になることは違う。**

## 6. PREVIEW / RETURN――報告ではなく、成果物を見て判断する

そしてRI#3では、PREVIEWがかなり重要だった。Machineが「生成完了」「Gate PASS」と報告しても、それだけではHuman Acceptanceにならない。Humanが採用するのはMachineの報告文ではなく、Actual Artifactである。画像なら実際の画像を見て、そこで初めて「使う」「使わない」を決められる。

だからHuman Decision Pointの近くには、出来るだけActual ArtifactのPREVIEWを置く。Artifactを見るために別Folderを開き、別Applicationを起動し、対象Fileを探す工程を減らす。判断材料と判断操作を近づけることで、Human Acceptanceが「PASSと書いてあるからOK」へ流れるのを防ぎやすくなった。

もう一つがRETURNである。意味変更、Scope変更、公開判断、受入れ判断のように、Machineが勝手に決めるべきでない地点へ来たらHumanへ戻す。重要なのは、ただ止めて「判断してください」と言うだけではなく、**何についてAuthorityが必要になったのかを分かる形で返すこと**だった。

## 7. STOPは失敗表示ではなく、Authorityを返す場所だった

以前の感覚だと、処理が止まればERRORである。だがHuman-facing Control Surfaceを作っていくと、STOPには別の役割が見えてきた。MachineがScope外へ出そうになった、意味が変わる、必要な情報が足りない、Human Acceptanceが必要になった。そこで勝手に補完せず止まるなら、それは必ずしも失敗ではない。

ただし「ERROR」だけでは人間が困る。必要なのはSTOP ReasonとNext Actionである。なぜ止まったのか。Humanが何を決めれば再開出来るのか。Retryでよいのか、設定変更なのか、Rejectなのか、Scopeを見直すのか。ここまで出て初めてSTOPが運用上のControlになる。

つまりSTOPは、Pipelineが壊れたことを知らせる赤ランプだけではなかった。**Machineが保持してはいけないAuthorityをHumanへ返すHandoff Point**にもなる。止まらないAIより、越えてはいけない境界で理由付きで止まれるAIの方が、Human-directedな仕事では扱いやすい。

## 8. AIの裏側を見なくても、Human-directedでいられた

こうして画面へ残すものを削っていくと、Human-facing SurfaceはBackendよりずっと単純になった。Humanが普段見るのは、Stage、Progress、Gate Result、STOP Reason、Artifact Preview、Decision Point、必要時のEvidence導線。Humanが操作するのは、Purposeや選択、Accept / Reject / ReturnのようなAuthorityを伴うものが中心になる。それ以外のMechanicalな処理は、決めた条件の中でMachineへ渡せる。

ここでようやく、記事タイトルの状態になった。**AIの裏側を見なくて済んだ。** 正確には、裏側が消えたわけではない。BackendもRuntimeもEvidenceも残っているし、必要になれば辿れる。ただ、仕事をするたびにHumanが全部を直接操作・監視しなくてもよくなった。

Human-facing Control Surfaceで整理したのは、大きく六つだった。

```text
SHOW
Humanが判断するために見せる

HIDE
通常運用では見せない

CONTROL
Humanが選ぶ

AUTO
承認済み条件の中でMachineが進める

PREVIEW
採用前にActual Artifactを見る

RETURN
Authorityが必要になったらHumanへ戻す
```

そこへStage / Progress、STOP Reason、Decision Point、Evidenceへの導線を重ねる。これでBackendの複雑さを隠蔽してHumanを無力にするのではなく、**HumanがPurpose、Judgment、Responsibilityを保持するために必要な面だけを切り出す**ことが出来た。

S3-05では、AIへ仕事を任せるには「どこまでMachineへ任せ、どこからHumanが決めるか」を先に設計する必要があると分かった。今回は、その境界を人間が実際に使える画面へ落とした。Human-directedは、Humanが全部を見ることでも、全部を操作することでもない。**Humanが見るべきものを見て、決めるべきことを決められる状態を作ること**だった。

## 「じゃあ、自分の画面では何を見せる？」を実際に設計する

ここまでが今回の無料Storyである。Backendを全部見せなくてもHuman-directedでいられること、SHOW / HIDE、CONTROL / AUTO、PREVIEW / RETURNへ分けるとHuman-facingな画面を整理しやすいこと、STOPにはAuthorityをHumanへ返す役割もあること。考え方と結果は、ここまでで閉じている。

ただ、自分のWorkflowへ持っていくと急に具体的な迷いが出る。「このStatusはSHOWかHIDEか」「このボタンはCONTROLとして残すのかAUTOへ回すのか」「Previewには何を置くのか」「どんな条件ならRETURNするのか」「STOP Reasonには何を書けば次の行動が分かるのか」。原則を知ることと、実際の1画面へ落とすことの間には、もう一段設計作業がある。

そこで今回、この再現作業をまとめた **「AIの裏側を見せない Human-facing Control Surface Design Pack」** を作った。Local AI Foundryそのものを導入するための資料ではない。ChatGPT、Claude、ローカルLLM、画像生成AI、AI Agentなど、今使っているAI Workflowを一つ選び、人間が見るべき面だけを設計するための実践Packである。

収録しているのは5点。

- README
- 紹介スライド
- 実践手順書
- 1枚チートシート
- かんたん設計Workbook

Packでは、対象Workflowの棚卸しから始めて、SHOW / HIDE、CONTROL / AUTO、PREVIEW / RETURN、Stage / Progress、STOP Reason、Decision Point、Evidence導線を順番に整理し、最終的に**自分のWorkflow用のHuman-facing Control Surface初版を1つ作る**ところまで進める。読むだけで終わる教材ではなく、実際に設計を残すためのPractical Layerとして作った。

価格は **1,980円**。無料本文では「なぜHuman-facing Control Surfaceが必要になり、どういう考え方へ辿り着いたか」という結果まで全部出す。有料Packでは、それを自分の仕事へ落とすための具体的な手順、Checklist、Workbook、実務Artifactを提供する。今回も境界は同じである。**結果は無料。再現方法が有料。**
