## 1. 前回までの宿題：AIは縛った。でも縛ったのはAIだけだった

03でContract Driven、04でDTO、05でNormalize、06でRetryを書いた。全部、AIエージェントの出力をどう縛るか、という話だった。

Planning、Research、Writing、Review。この4段階は、DTOとGateとNormalizeとRetryで、かなり手堅く固まった。AIが確率的に失敗する前提で、失敗しても被害が広がらない境界を先に置く。この設計思想は、01〜06を通してずっと一貫していた。

でも実際に手を動かしてみると、AIを縛っただけでは終わらなかった。**縛られていないものが、まだ残っていた。人間側の運用そのものだった。**

## 2. 同じ設定なのに、6つの顔を持っている

Local AI Foundryは、DifyのWorkflowをGUIで編集する。GUIで直した内容は、エクスポートするとDSLになる。DSLはGitに置く。Gitの内容を人間が読んで、Documentationに反映する。そして実際に動くのは、Dify上のRuntimeだ。

architecture.mdには、これが図解されている。

```
GUI / Dify Draft ──┐
DSL / Git ──────────┼──▶ Configuration Management ──▶ Configuration Item単位の採用判断 ──▶ 正本・派生物・証跡の同期
Documentation ──────┤
Runtime / Run graph ┘
```

同じ「一つの設定」のはずなのに、その姿は少なくとも、Dify Draft、Published Workflow、エクスポートされたDSL、Git上の定義、Documentation、Runtimeの実効状態という6か所に分かれる。しかも、それぞれの更新タイミングがバラバラだ。GUIをいじった瞬間に更新されるものもあれば、Gitにpushするまで反映されないものもある。Documentationに至っては、人間が気づいて書き直すまでずっと古いまま残る。

ADR-0009の背景には、こう書かれている。

> これらは更新契機、保存形式、反映タイミングが異なるため、Workflow全体を一つの成果物だけで完全に表現することはできない。

## 3. 「どれか一つを正本にする」を却下した理由

一番シンプルな解決策は、「どれか一つを正本にして、残り全部をそこに合わせる」ことだ。例えばGitのDSLファイルを唯一の正本にして、GUIの変更は全部Gitに同期する。あるいは逆に、GUIを正本にしてGitは単なるバックアップにする。

これも却下されている。理由はこうだ。

> GUIまたはエクスポート定義の一方を無条件に正本として全面同期すると、他方にだけ存在する有効なPrompt、Code、Gate条件、Runtime Parametersなどを失う可能性がある。

これは04〜06で繰り返し出てきた話と同じ構造だ。「一括で片方に揃える」というのは、一見スッキリしているが、実際には片方にしか存在しない有効な情報を握りつぶすリスクを抱える。GUIで急いで直したPrompt調整が、Gitへの一括同期で消えてしまう。逆に、Gitで直したGate条件が、GUIへの一括反映で上書きされてしまう。どちらの方向にも、この種の事故が起きうる。

## 4. 採用した答え：Configuration Item単位で正本を持つ

ADR-0009が採用したのは、「Workflow全体」という粒度をやめて、もっと細かい「Configuration Item」という単位で管理することだった。

ADR-0009では、Configuration Itemに少なくとも次を含めるとされている。

**対象そのもの**
- GraphとEdge
- Promptと変数参照
- Codeノード
- DTO、Normalize、Contract Gate
- LLM Node Parameters
- Provider Settings

**それらが存在する表現・保存・実効状態**
- DraftおよびPublished Workflow
- Workflow定義（DSL）
- Git
- Documentation
- Runtimeの実効状態と実行証跡

そして、それぞれのConfiguration Itemごとに、正本・派生物・実効状態・同期方向・変更理由・検証結果を個別に持たせる。「Workflow全体でどっちが正しいか」を決めるのではなく、「このPromptはGitが正本」「このRuntime Parameterは今Draftの方が新しい」というふうに、粒度を細かく分けて判断する。

これは03で書いたContract Drivenの発想と地続きだ。あのときは「Agent間の受け渡しを、一つの会話ではなく、フィールドごとに意味を固定したDTOにする」という話だった。今回は「Workflow全体の状態を、一つの正本ではなく、Configuration Itemごとに意味を固定した管理単位にする」という話になっている。**粒度を細かくして、意味を混ぜないという原則が、AIの出力管理から、人間の運用管理にまで拡張されている。**

## 5. 一致・不一致だけでは足りない。8つの状態

Configuration Itemごとの差分は、単に「一致してるか、してないか」の2択では表現しきれない。ADR-0009は、状態をこう分類している。

- `Synchronized`（同期済み）
- `Equivalent`（表現は違うが意味は同じ）
- `Draft Newer`（GUI側が新しい）
- `Definition Newer`（DSL/Git側が新しい）
- `Runtime Drift`（実行時の実効状態がズレている）
- `Intentional Temporary Drift`（意図的な一時的なズレ）
- `Conflict`（衝突していて自動判断できない）
- `Unknown`（原因不明のズレ）

この中で一番重要なのは、`Intentional Temporary Drift`と`Unknown`の違いだと思う。運用原則にはこう書かれている。

> 開発途中では、追跡可能なTemporary Driftを許容する。一方で、原因、意図、終了条件が不明なUnknown Driftは許容しない。

「今は意図的にズレさせている、終わったら戻す」というズレは許す。でも「なぜズレているのか誰も分からない」というズレは許さない。06のRetryと同じく、曖昧な状態を曖昧なまま通過させない設計だ。

暫定変更には、対象・終了条件・復帰先・検証記録を持たせることが義務付けられている。「とりあえず動くからこのままにしとこう」という、期限のない暫定運用を許さない設計だ。

## 6. 白状する。今もまだ、終わっていない

ここまで読むと、Configuration Managementという仕組みを導入して、全部きれいに片付いたように見えるかもしれない。

実際はそうではない。status.mdの現在状態にはこう書かれている。

> Published WorkflowはConfiguration Synchronizationの比較対象外である。Current Baselineは`Provisional / Blocked`であり、既知Configuration Driftの採用判断は未完了である。

Current Baseline（現在の基準状態）自体が、`Provisional`（暫定）かつ`Blocked`（ブロック中）だ。しかも、すでに検出されているConfiguration Driftについて、どちらを採用するかという判断自体がまだ終わっていない。

Contract、DTO、Normalize、Retryは、01〜06で見てきたように、それぞれ「有限に区切って、判断できないものは止める」という形で決着している。Contract GateやRetryには明確な終了条件がある。通るか、止まるかだ。

しかしConfiguration Managementが問うのは、「動いたか」ではなく、「今の構成を正式な基準状態として採用できるか」である。Workflow自体は動く。Retryも尽きていない。Gateも通っている。それでも、「今の構成が本当に正しい状態か」という一段上の問いには、まだ答えが出ていない。`Provisional / Blocked`というステータスは、いわば「動いてはいるが、まだ正式版とは言い切れない」という宙ぶらりんな状態を、隠さずそのままステータスとして表明している。

これは04・05・06のときのような「一度は起きたが、もう対処法が分かっている」失敗ではない。**今この瞬間も、答えが出ていない問い**だ。

## 7. まとめ

Contract、DTO、Normalize、Retryは、「AIがどう失敗するか」を相手にした設計だった。全部、生成物という一つの層の中の話だった。

Configuration Managementは、そこから一段上がった話になる。GUI、Draft、DSL、Git、Documentation、Runtime。これは全部、人間が触る場所だ。AIを完璧に縛っても、人間が6つの場所に同じ設定をバラバラに保存している限り、「今、本当に動いているものは何か」という問いは消えない。

すべて直した。Contract Gateも、Normalizeも、Retryも、設計通りに動いている。**それでも、終わらなかった。**Configuration Managementという最後の壁は、今もまだ`Provisional / Blocked`のままだ。

次は、この宙ぶらりんな状態を、どう検証すればいいのかという話をする。**Runtimeを見ないレビューは、レビューではない。**
