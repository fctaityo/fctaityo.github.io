## 1. 世界のAI議論、今どこに向かってるのか

最近、AIを実運用していて、どうしても引っかかることがあった。

「LLMに正しいPromptを書けば、本当に正しく動くのか？」

自分が運用しているLFでも、この違和感がずっと消えなかった。

で、これ自分だけの感覚かと思って世界の議論を漁ってみたら、複数のコミュニティ・企業・研究がほぼ同時に同じ結論に辿り着いてた。

結論を先に言う。

> LLMに「正しく考えさせる」だけでは足りない。
> LLMが勝手な行動を選べないよう、実行境界を決定論的に制御する必要がある。

これが今、世界のAI議論が向かってる方向。あとで紹介するが、自分が運用しているLFでも、かなり近い考え方を採っていた。順番に見ていく。

## 2. Anthropicの「Workflow」と「Agent」の切り分け

まずAnthropic自身が、固定された処理経路をたどる「Workflow」と、LLMが自分で処理やTool利用を決める「Agent」を明確に区別してる。定義済みの作業ではWorkflowの方が予測可能性と一貫性が高いという立場で、逆にAgentは柔軟性が必要な未定義問題向け、裁量を信頼できる場面で使うものとしている。

つまり公式ですら「単純作業にLLMの裁量を持ち込むな」と言ってるに等しい。

## 3. OpenAIも同じ結論に辿り着いてる

OpenAIはStructured Outputsの説明で興味深いことを言ってる。モデル性能を上げるだけでは必要な信頼性に届かなかったから、決定論的な制約付きデコードを追加してSchema適合率を100%にした、と。

要するに「モデルを賢くするだけでは足りず、選択肢そのものを構造的に制限する」という発想を、公式に採用したということ。これ、LFがContract GateやDTOでやってることと発想が同じ。

## 4. Hacker Newsの現場感がわりと生々しい

コミュニティ側の議論はもっと直接的で現場寄り。

Promptに「10件以上削除するな」と書いても、長いContextや例外条件が絡むと普通に無視される。だからTool実行の直前に別のValidation LayerやHard-codedな条件を置くべきだ、という意見が出てる。

別のスレッドでは、LLMが提案したActionをPolicy EngineがAllow / Deny / Escalateしてから実行する構成が紹介されてて、「Authorizationは契約じゃなく構造にしろ」という表現が使われてる。

さらに根本的な指摘もある。企業システムは決定論的なのに、LLMは確率的。この不一致が問題の本質だから、LLMはDecision MakerじゃなくSuggestion Engineとして扱い、実行は決定論的なControl Layerに任せるべきだ、という主張。

これはLFの思想とほぼ同じ方向を向いてる。

## 5. 「機械的作業からLLMを外す」という実例

GitHub上のAgent framework調査でも似た報告がある。

Promptだけで運用してたときは、Agentが必須のRSS取得工程を平気で飛ばした。でも機械的な収集処理をLLMから完全に外して、決定論的なPython処理に置き換えたら、その失敗モード自体が消えた。

この報告の核心はこう。

> より良いPromptを書くのではなく、機械的工程ではLLMをCritical Pathから外す。

価格確認、CI状態取得、監視、定型収集のような作業にも一般化できるとされてる。「単純作業では裁量がむしろ害になる」という話、これもLFの現場感覚と一致する。

## 6. 2026年の研究、もっと直接的に踏み込んでる

2026年に入って、かなり直球の研究も出始めてる。

「Deterministic Control Plane for LLM Coding Agents」は、Agent設定・Permission・Phase State・Audit LogをLLM任せにせず、LLMより上位の決定論的Control Planeで管理すべきだと主張してる。Governanceを別のLLM orchestrationに委譲してはいけない、とまで明記されてる。

「Organizational Control Layer」は、LLMによる提案生成と外部環境へ影響する実行を分離して、Action実行前にPolicy EnforcementとEscalationを挟む構成を提案してる。複数モデルで検証した結果、危険な実行を88%からほぼゼロまで減らせたという報告もある。

「Before the Tool Call」は、Tool Callごとに宣言的Policyを評価して、許可されなければ実行しない方式を提案してる。PromptやAlignmentはしょせん確率的だから、Action単位の決定論的Authorizationが要る、という立場。

ここまで来ると、LFがやってきたことの学術的な裏付けがかなり揃ってきた感じがある。

## 7. 面白いのは「裁量を全部消せ」じゃないこと

ここまで読むと「じゃあLLMの裁量って全部悪なのか」と思うかもしれないけど、最先端の議論はそこまで極端じゃない。役割を分けてるだけ。

```text
曖昧・創造的・探索的な仕事
→ LLMの裁量を使う

機械的・可逆性が低い・証跡必須の仕事
→ 決定論的Workflowへ移す

外部へ作用する直前
→ Policy / Gate / Authorizationで拘束する
```

Anthropicも、明確に分解できるTaskではWorkflowを使い、未知の手順が必要なTaskではAgentを使うという整理をしてる。全否定じゃなく、住み分け。

## 8. LFとの一致点

LFで組んできた要素——DTO、Contract、Contract Gate、Bounded Retry、Configuration Management、Definition of Done、Evidence、Human Authorization、Project State、Publication Governance——は、今世界で出てるこの議論とほぼ同じ方向を向いてる。

特に一致してるのはここ。

> AIの正しさを信用するのではなく、正しくない選択が実行されない構造を作る。

これがLFの根っこにある思想であり、今の世界の議論の中心にある思想でもある。

## 9. 実際にLFで運用していて気付いたこと

ただ、正直に言うと世界の議論の多くは、まだ

- JSONを壊さない
- Tool Callを制限する
- 危険なActionを拒否する
- DatabaseやPaymentを守る

という「出力・実行境界」の話に集中してる。

一方、LFの運用で実際に問題になったのは、「確認して、と言われたら必ずGitHubを読む」みたいな、業務手順そのものの拘束だった。これはSecurity Guardrailより明らかに広い範囲の話。

LFが扱ってるのは、

- 何を読むか
- どの順番で読むか
- 何を証跡とするか
- いつ完了と言っていいか
- 何を勝手に変更してはいけないか

という、Operational Contract全体。ここまで一体化して運用基盤に組み込んでる事例は、少なくとも自分が見た範囲ではまだ少ない。

## 10. まとめ

世界では今、

- Agent Safety
- Runtime Governance
- Deterministic Control Plane
- Policy-bound Execution
- Workflow over Agent

という別々の名前で、実質同じ問題を掘り始めてる。

LFはそれを、「AIの裁量を、業務単位・文書単位・状態遷移単位で削る」という形で統合してやってきた。

つまりこの話、孤立した個人プロジェクトの思想じゃない。むしろかなり時流の中心に近い。ただしDocumentation・Publication・State・Evidenceまで全部を一つの運用基盤に統合してる例は、まだ珍しい。

AIが賢くなるほど、裁量も増える。

だからこれから必要なのは、AIを信用する技術じゃなく、AIを信用しなくても運用できる技術なのかもしれない。
