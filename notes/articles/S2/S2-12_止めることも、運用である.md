前回のS2-11は、少し変わった終わり方をした。Repository、Draft、Published、Canonical Launcher、Formal Input BindingまでCurrentへ揃い、Fresh RV-01 Authorizationも`GRANTED / NOT CONSUMED`。あとはFinal Pre-Runtime Gateを通し、Fresh Formal RV-01を一度だけ実行すればよいところまで来ていた。それでもCurrent Candidate Runtimeは`NOT EXECUTED`、Runtime Acceptanceは`PENDING`のままだった。

だからワシは最後に、「Fresh RV-01はまだ走っていない。だからこの記事も、ここで一度止める」と書いた。普通なら、その次の記事はFresh RV-01の結果報告になる。PASSしたのかFAILしたのか、実際のRuntime Evidenceを見て何を判断したのかを書くはずだった。

ところが、そうはならなかった。Fresh RV-01は走らず、RI#1 Article Productionは`FROZEN / HISTORICAL BENCHMARK`として止めることになった。今回は、なぜ「実行できるのに実行しない」という判断が成立したのか、その話をする。

## 1. 前回、ワシらは「ここで止める」と書いた

S2-11を書いた時点では、Fresh RV-01を実行する前提はまだCurrentだった。Correct Contract下で一度FAILしたFormal RV-01を受けて、Retry CorrectionをRepositoryへ入れ、Draft / Publishedへ反映し、Publish後にずれたCanonical LauncherもCurrent Publishedへ同期した。失敗したまま放置していたわけではなく、むしろFresh RV-01を正しい条件でやり直せるところまで、かなり丁寧に整えていた。

当時の状態を並べると、こうなる。

```text
Repository
CURRENT

Draft
CURRENT

Published
CURRENT

Canonical Launcher
CURRENT

Formal Current Source
CURRENT

Current Candidate Runtime
NOT EXECUTED

Fresh RV-01 Authorization
GRANTED / NOT CONSUMED
```

この断面だけを見れば、次の一手はFresh RV-01である。少なくとも2026-08-14時点では、それが正しかった。

しかしその後、Local AI Foundry全体ではRI#2 Documentation Production、RI#3 Visual Asset Production、RI#4 Research-Grounded Long-form Content ProductionのEvidenceが増えた。Article Productionだけを追っていた頃には見えなかったControl Patternが、別の仕事でも繰り返し現れ始めたことで、Projectの問いそのものが変わっていった。

最初は「記事生成Workflowをどう壊さず完成させるか」だった。そこから「人間が責任を持ったまま、異なる仕事をAIへどう任せるか」へ広がり、現在は「複数のReference Implementationで共通して必要になったControl Structureのうち、何をFoundry Coreとして再利用できるのか」を見る段階へ進んでいる。Fresh RV-01が不要になったわけではない。ただ、Project全体のCurrent Purposeに対する優先度が変わった。

## 2. Fresh RV-01は、結局走らなかった

ここは曖昧にしない。Fresh Formal RV-01は実行していない。「たぶん今度は通っただろう」とも書かないし、「最後までやっていないからRI#1は失敗だった」とも書かない。残っている事実は、そのまま残す。

```text
Historical Correct-Contract Formal RV-01
FAILED

Fresh Formal RV-01
NOT EXECUTED

Runtime Acceptance
PENDING

RI#1 Current Role
FROZEN / HISTORICAL BENCHMARK
```

Historical Correct-Contract RV-01では、Conclusionが初回623文字、Retry後698文字となり、Expected Range 240〜420へ収束しなかった。そのFailureを受けてDeterministic Retry Correctionを入れ、RepositoryだけでなくDraft / Published / LauncherまでCurrentizeした。だが、そのCorrection後CandidateをFresh RV-01として実行した結果は存在しない。

だから、PASSにもFAILにもできない。実行していないものは、実行していない。それだけの話なのだが、Projectを前へ進めようとすると、この未完了を都合よく丸めたくなる。「もう十分直したから実質OK」「前のRunがFAILしているから結局ダメ」「FreezeにしたならPENDINGも閉じよう」。どれも説明としては簡単になるが、やればHistorical EvidenceをCurrent都合で書き換えることになる。

Local AI Foundryでは、それをしない。過去のFAILEDも、未実行のFresh RVも、PENDINGのRuntime Acceptanceも、それぞれ別の事実として残す。そのうえで、RI#1の現在の役割だけを変える。

## 3. GateはPurposeではない

今回いちばん大きかったのは、ここだと思う。Fresh RV-01はRemaining Gateだった。しかしGateは、それ自体がProjectの目的ではない。

```text
Gate
≠
Purpose
```

Runtime Verificationなら、「Current Candidateを実際に動かした時に何が起きるか」を確認し、Runtime Acceptanceを判断するためにある。RI#1をCurrent Mainlineとして完成させることがProjectの目的であり続けるなら、Fresh RV-01を実行する意味は大きい。

では、ProjectのCurrent Purposeが変わったらどうなるのか。Gateが残っているという理由だけで、それを必ず消化しなければならないのか。今回、ワシらはそう考えなかった。

RI#2〜RI#4のEvidenceが増えたことで、Projectは一つのReference Implementationを最後まで磨き切ることより、複数RIを比較して再利用可能なControl Structureを見つける方向へ進んだ。実際、Cross-RI Evidenceから最初のConfirmed Foundry Coreとして`FC-CORE-001 Runtime Capability Calibration`も成立した。Foundry Coreの詳しい話はSeason 3に回すが、少なくとも「RI#1だけを完遂すること」がProject全体のCurrent Purposeではなくなった。

ここでFresh RV-01を実行することは技術的にはできる。しかし、できることと、今やるべきことは同じではない。Governanceを真面目に作るほど、「Checklistがあるから埋める」「Gateがあるから通す」「未完了があるからCompleteにする」という発想に引っ張られやすい。そのうち、本来のPurposeより「全部緑にすること」の方が強くなる。

Season 2でずっと扱ってきた`Current`という考え方は、Taskにも効く。昔CurrentだったNext Actionが、今もCurrentとは限らない。

## 4. FreezeはFailedでもCompleteでもない

RI#1を止める時、最初に困るのは「では、何と呼ぶのか」である。`Failed`にすると話がおかしい。Historical Runには`FAILED`があるが、Correction後CandidateはFresh RVを実行しておらず、そのCandidateが失敗したEvidenceは存在しない。

逆に`Complete`や`Runtime Accepted`にもできない。Fresh RVは`NOT EXECUTED`で、Runtime Acceptanceは`PENDING`だからだ。削除する理由もない。RI#1からはContract、DTO、Normalize、Retry、Configuration Management、State、Human Decision Boundary、Binding、Runtime Verification、Evidenceなど、大量の知識が得られている。

だから、`FROZEN / HISTORICAL BENCHMARK`とした。

```text
Freeze
≠
Failed
≠
Deleted
≠
Accepted
```

ここでいうFreezeの意味は、「新しいMainline Runtime検証は進めない」「過去の成立・失敗・未実行Evidenceは残す」「Cross-RI比較のBenchmarkとして参照する」の三つである。未完了を成功扱いするための便利な箱ではない。

この区別はかなり重要だと思う。気に入らない結果が出たからFreeze、難しくなったからFreeze、AcceptanceできないからFreeze、では単なる逃げ道になる。今回成立しているのは、Historical Stateを成功側へ一切書き換えず、なぜCurrent Mainlineから外すのかを別のHuman Decisionとして持っているからだ。

停止理由と実行結果を混ぜない。これもまた、Season 2で何度も扱ってきた責任境界の話だった。

## 5. 止める判断にもEvidenceが要る

Human Authorityというと、つい「GOを出す権限」を想像する。Publishしていい、Runtimeしていい、Commitしていい、このCandidateを採用する。もちろん、それらはHuman Decisionである。

ただ、今回もう一つ分かった。Human Authorityには、続けないと決める権限も含まれる。

Fresh RV-01 Authorizationは`GRANTED / NOT CONSUMED`だった。つまり、実行してよい状態にはなっていた。それでも実行しなかった。Authorizationがあるからといって、必ず消費しなければならないわけではない。Authorizationは「実行しろ」という命令ではなく、定義されたScopeの中で実行してよいという許可である。

Current Purposeが変わり、別のEvidenceを優先する意味が生まれたなら、HumanはそのAuthorizationを使わず止めることができる。ただし、気分で止めればいいわけでもない。今回のStop Decisionには、Fresh RV直前までCurrentizeされたRI#1の状態、Fresh RVが`NOT EXECUTED`である事実、Runtime Acceptanceが`PENDING`である事実、Historical FAILED Run、RI#2〜RI#4から増えた比較Evidence、そしてProjectのCurrent VectorがCross-RI Evidence → Foundry Core Extractionへ移ったという背景がある。

つまり、停止もEvidenceなしの気分ではない。

```text
Continue
→ Current Purposeに必要なら進める

Stop
→ Current Purposeに対する意味を再評価して決める

どちらも
→ Evidence + Human Decision
```

S2-06では、Human Gateを増やしすぎるとHumanが単なるContinueボタンになるという話をした。今回の件は、その逆側から同じことを見せている。HumanはContinueボタンではない。何を続け、何を止めるかまで含めて、Purposeに対する責任を持つ。

## 6. Season 2で作っていたのは「正しく止められる境界」でもあった

Season 2を最初から振り返ると、ずっと「分ける」話をしていた。Configurationをコードと分け、Project StateとActive Workを分け、LatestとCurrentを分けた。Human DecisionとMechanical Continuation、Canonical SourceとPartial Source、「作った」「Repositoryへ反映した」「Published」も分けた。

さらに、Humanが決めた値とAIが考える値を分け、Machineが知っているFactとLLMへ任せるSemantic Workを分け、最後にはPublishedとRuntime Acceptedも分けた。一見すると、ひたすら境界を増やしてきたSeasonだったとも言える。

でも今回、その意味が最後に繋がった。

もし全部を一つの`DONE / NOT DONE`だけで管理していたら、RI#1を止める時に困る。Fresh RVをやっていない。Runtime Acceptanceも終わっていない。しかしProject全体は次へ進みたい。この状態を一個のStatusだけで表そうとすれば、「失敗」「未完了」「完了」のどれかへ無理やり押し込むしかない。

実際には、状態を分けて持っている。

```text
Project State
Published

RI#1 Role
FROZEN / HISTORICAL BENCHMARK

Fresh RV-01
NOT EXECUTED

Runtime Acceptance
PENDING

Historical FAILED Evidence
PRESERVED

Project Current Vector
Cross-RI Evidence → Foundry Core Extraction
```

これは矛盾ではない。全部、違う問いへの答えだからだ。

Season 2でやっていた「境界を決める」という作業は、壊れないためだけではなかった。未完了のものを未完了のまま残し、それでも別のCurrentへ安全に進むためでもあった。

正しく止めるためには、正しく分けておく必要がある。

旧S2-12で考えていた「境界を決める」というテーマは、消えたわけではない。むしろ最後まで残って、今回の「止めることも、運用である」に繋がった。

## 7. RI#1は止まる。でもEvidenceは次へ行く

RI#1 Article Productionは、ここで止まる。Fresh Formal RV-01は走らない。Runtime Acceptanceは`PENDING`のままHistorical Stateとして残り、Historical Correct-Contract Formal RV-01の`FAILED`も残る。Correction後CandidateがFresh RVで成功したという物語は作らない。

その代わり、RI#1から得たEvidenceは残る。そしてRI#2、RI#3、RI#4と比較される。

ここから先の問いは、「RI#1をどう完成させるか」ではない。Article Production、Documentation Production、Visual Asset Production、Research-Grounded Long-form Content Productionという全く違う仕事をAIへ任せた時に、なぜ同じようなControlが何度も必要になったのかを見る。

Runtime Capabilityを事前に決め打ちせず測る。Technical Gateを通ってもHuman Acceptanceとは別に扱う。Human-facing Control Surfaceを置いて、裏側のRuntimeを人間から隠す。Searchできることと、Research Groundedな成果物になることを分ける。Dify、n8n、Ollama、ComfyUI、SearchといったPlatformそのものをFoundryと決めつけず、その上で共通して必要だったものを探す。そうした話がSeason 3へ続いていく。

Season 1では、壊れないAI Workflowを設計した。Season 2では、その仕組みをどう変更し、同期し、判断し、公開し、実行し続けるかを扱った。そして最後に残ったのは、意外にも「続ける方法」だけではなかった。

作ったものを守るだけが運用ではない。何を続け、何を止め、何を次へ持っていくかを決めることも運用である。

RI#1はここで止まる。だが、RI#1から見つかったものは、ここから別の仕事へ持っていく。

Season 2、完。
