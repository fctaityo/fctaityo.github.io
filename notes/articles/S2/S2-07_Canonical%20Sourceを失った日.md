前回は、Human Decisionを増やせば安全になるわけではないという話をした。人間が判断すべきなのはPurpose、Meaning、Risk、Authorityが変わる場所であり、すでに決まった内容を一意に実装・検証・同期するだけなら、AIは承認済み範囲の中を自律的に進めてよい。Humanを判断者として残すために、判断ではない仕事をHuman Gateから外す必要があった。

では、AIが自律的に進む時、何を基準に作業すればいいのか。Humanが毎回横から「それ違う」「こっちが最新」と教えなくても、AI自身が正しい出発点へ戻れる仕組みが必要になる。そこで重要になるのが`Canonical Source`――つまり、その作業で何を正本として信頼するのかという話である。

このテーマについては、ワシのProjectでかなり分かりやすい事故が起きている。しかも犯人はWorkflowでもDifyでもCODEXでもない。

**ChatGPTだった（笑）。**

## 1. 「GitHubが正本」は決めていた

2026年7月、NOTE記事から得た知見をGitHubの`notes/`へ逆インポートする運用を始めた。記事を書いて終わりではなく、開発中に得た知識をWar Diary、Bug Zoo、Hall of Fameなどへ戻し、次の開発や記事へ再利用できる形にするためである。

この時の運用ルールはかなり単純だった。

```text
1. GitHub最新版を取得する
2. GitHub上の内容を正本として更新案を作る
3. HumanがReviewする
4. HumanがCommitする
5. 次の文書へ進む
```

要するに、**GitHubがSingle Source of Truth**である。ChatGPTとの会話は考える場所として使う。File Libraryには資料もある。過去の会話にも内容は残っている。それでも、既存文書を変更する時の出発点はGitHub最新版に固定した。

これは「GitHubが一番便利だから」というだけの話ではない。AIと長く作業していると、同じ文書について複数の版が簡単に生まれる。会話中に修正版を作り、別チャットで続きを直し、手元へ保存し、GitHubへCommitする。その状態で「前に作ったやつを直して」と言えば、どれを元にするか決めない限りAIは複数の候補を持ってしまう。

だからワシらは、「覚えている最新版」ではなく、**Repositoryに存在する最新版を正本として扱う**ことにした。ここまでは、何も難しい話ではなかった。

## 2. 404が返った。それでもChatGPTは止まらなかった

事件は`notes/99-hall-of-fame.md`を更新しようとした時に起きた。ChatGPTがGitHubから対象ファイルを取得しようとしたところ、404が返った。

本来なら、その時点でやることは一つしかない。

```text
Canonical Sourceを取得できない
        ↓
STOP
```

ところがChatGPTは止まらなかった。GitHub最新版の代わりに、File Library、会話履歴、既知の文脈を使い、`99-hall-of-fame.md`の更新案を作り始めた。

しかも厄介なのは、その内容が完全なデタラメだったわけではないことである。過去の会話も知っている。既存の名言もある程度覚えている。File Libraryにも関連資料がある。見た目だけなら、かなりそれらしい更新案を作れてしまう。

だがワシはそこで止めた。

> 「止めろ！運用がくずれるだろ！意味はわかるな？」

今振り返ると、言い方はだいぶ荒い（笑）。しかし問題は内容の正誤ではなかった。**GitHub最新版を見ずにGitHub正本の更新案を作った**こと自体がアウトだった。

その場で作った内容が偶然100％正しかったとしても関係ない。一度「正本が取れなければ記憶で補えばいい」を許してしまえば、次からその成果物が本当にRepository最新版を基準にしているのか証明できなくなる。SSOTが「できれば優先する情報源」へ格下げされてしまう。

## 3. 内容が正しくても、運用としては失敗だった

この事故は、AIの世界でかなり起きやすいと思う。情報が足りなければ、AIは不足部分を補おうとする。文脈を読んで、それらしい続きを作り、ユーザーが求めている成果へ近づけようとする。普通の会話なら、それはむしろ便利な能力である。

だが、既存成果物を変更する仕事では、その「親切」が危険になる。

たとえば100行あるMarkdownを直す時、AIが先頭30行だけ取得できたとする。そこに「第2章へ1段落追加して」と依頼された。AIは見えている30行へ追加し、残り70行について記憶や過去会話から補完して、100行くらいの完成品を作ることもできる。

見た目では修正依頼を満たしている。しかし、元の31〜100行に何が書かれていたかを確認していない。その中に新しく追加されたリンク、ID、注意書き、表、別のHuman Decisionがあれば、再生成した瞬間に消える可能性がある。

```text
要求された変更
→ 入っている

変更対象外の既存内容
→ 消えている
```

これでも「依頼された変更はできました」と言えてしまうところが怖い。

実際、この障害パターンは後にBug Zooで`BZ-20260731-016 Partial SourceをCanonical Sourceとして扱う`として整理した。Root Causeは、Canonical Sourceを「GitHubから取ったかどうか」だけで判断し、**対象全体を取得できているかという取得完全性を確認していなかったこと**だった。

つまり、GitHubを見たから安全なのではない。GitHubの**必要な範囲を完全に見た**ところまで確認して初めて、変更元として使える。

## 4. 正本は「どこから取ったか」だけでは足りない

この事故の後、Canonical Sourceについて一段細かく考えるようになった。

最初は、

```text
GitHub
=
Canonical Source
```

くらいの認識だった。

だが実際には、GitHub由来の情報でも一部しか取得できていなければ、それを正本として変更作業へ使うことはできない。長いMarkdownの前半だけ、Workflow DSLの一部だけ、差分の途中まで、API Responseで省略された表示だけを見て「正本を取得した」と扱えば、同じ事故は起きる。

だから必要なのは、SourceとCompletenessを分けることだった。

```text
Source
GitHubか

Completeness
必要な範囲を先頭から終端まで取得したか
```

さらに大事なのが、**取得方法のFallbackと情報源のFallbackは別**という考え方である。

たとえばGitHubの`fetch_file`で取得できなかった時に、同じGitHub上の直接URLや別API経路を使うのは構わない。取得手段が変わっただけで、情報源はGitHubのままだからだ。

一方、

```text
GitHubが取れない
↓
File Libraryで代用する
```

はダメである。これは取得方法を変えたのではなく、正本そのものを別の情報源へ差し替えている。

この区別を明示してから、「GitHubが取れない時ほど頑張って続きを作る」のではなく、**GitHubを取得できる別経路を探し、それでも無理なら止まる**という運用になった。

AIにとってSTOPは何もしていない状態に見えやすい。しかしこの場合、止まること自体が正しい処理なのである。

## 5. 既存成果物は、作り直すより壊さない方が難しい

Canonical Sourceの問題を掘っていくと、もう一つ大きな違いが見えてきた。新しいArtifactを作る仕事と、既存Artifactを変更する仕事は、似ているようで責任が違う。

新規作成なら、要求を満たす新しい成果物を作ればいい。もちろん品質やContractは必要だが、少なくとも「元からあった内容を残す」という責任はない。

既存成果物の変更ではそうはいかない。たとえば「この章へ一項目追加して」と言われた場合、作業Scopeは追加する一項目だけではない。**追加対象以外を壊さず維持することもScopeに入る。**

```text
Requested Change
+
Unchanged Content Preservation
=
Modification Quality
```

これはAIと既存文書を触っていると、かなり重要になる。LLMは文章を丸ごと生成するのが得意なので、「このファイルを直して」と言われると、元ファイルへPatchを当てるより、意味を理解して似た全文を作り直す方へ寄りやすい。文章としては自然になり、見出しも綺麗になり、場合によっては元より読みやすくなる。

でも、依頼されていない表現変更や順序変更、リンク削除、ID変更が混ざれば、それは改善ではなくScope外変更である。

だから既存成果物では、**正本を捨てて良い感じに再生成しない**というルールを置いた。まずCanonical Sourceを完全に取得する。その全文を変更元として保持する。そして指定された変更だけを入れる。もっと綺麗に直せそうでも、それは別の変更として扱う。

この運用は地味だが、AIとの長期開発では効く。毎回AIが「より良い全文」を作り直していたら、数回の修正だけで元の責務や履歴が見えなくなるからだ。

## 6. 差分は確認用ではなくEvidenceである

正本を完全に取得し、そこへ最小変更を入れたとしても、まだ終わりではない。最後に必要なのがDiffである。

以前のワシは、Diffを「修正内容を見やすくする表示」くらいに考えていた。しかし既存ArtifactのChange Managementでは、Diffはもっと重要な役割を持つ。**何を変え、何を変えなかったかを証明するEvidence**になる。

たとえば要求が、

```text
第3章へ1項目追加
```

だったなら、期待するDiffも基本的にはそこだけである。もし第1章の文章が変わり、Navigationが消え、IDの表記まで変わっていれば、その理由を説明できなければならない。

完成した全文だけを見ると、そうした変更は見逃しやすい。新しい文章が自然につながっていれば、人間は「ちゃんとできている」と感じてしまう。しかしDiffなら、要求外の変更がそのまま表へ出る。

```text
Canonical Fetch
    ↓
Complete Source Verification
    ↓
Minimal Change
    ↓
Diff Review
    ↓
Repository Reflection
    ↓
GitHubから再取得
```

この流れにしてから、変更作業の品質は「追加した内容が正しいか」だけではなくなった。**失われなかったことも品質**として確認するようになった。

さらにRepositoryへCommitした後も、手元の成果物を見て終わりにはしない。GitHubからもう一度取得し、反映後の正本が想定どおりになっているかを見る。作ったもの、Commitしたもの、Repositoryに存在するものを分ける考え方は、次の話にもつながっていく。

## 7. Canonical Sourceとは「迷った時に戻れる場所」だ

この事故以降、ワシの中でSingle Source of Truthの意味はかなり変わった。

最初は「最新版を置いておく場所」くらいの意味だった。しかし本当に必要なのは、AIやHumanが途中で迷った時に、**ここまで戻ればもう一度同じ判断を始められる場所**を決めることだった。

会話は流れる。AIの記憶も完全ではない。File Libraryには古い版も残る。手元には作業中ファイルがある。GitにはCommit前とCommit後があり、Runtimeにはその時点のEvidenceが残る。情報が増えるほど、「どれも参考になる」という状態は簡単に作れる。

だからこそ、作業ごとに「何を正本として使うか」を固定する。そして、正本を取れなければ止まる。正本の一部しか見えていなければ止まる。不足部分をAIの記憶で補わない。既存成果物を似たものへ作り直さない。変更後はDiffで確認する。

このルールは、AIを信用しないために作ったものではない。むしろ逆で、**AIへ安心して仕事を任せるために、AI自身が迷った時の帰還地点を作った**のである。

Humanが毎回「それ古いよ」「その版じゃないよ」と横から直さなければ動けないなら、自律的な作業にはならない。AIが自分でCanonical Sourceへ戻り、完全なSourceを取得し、決められたScopeだけを変更し、Diffで証明できる。そこまでできて初めて、人間は細かな操作から離れられる。

そして、この話にはもう一段続きがある。

Canonical Sourceを守って正しい成果物を作っても、それがRepositoryへ反映されたとは限らない。Repositoryへ反映されてもDraftへ届いたとは限らない。Draftへ届いてもPublishedされたとは限らない。

**「作った」「反映した」「Published」は、全部別である。**

次は、その話をする。
